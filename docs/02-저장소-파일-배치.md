# 저장소 파일 배치 확정

> 구현 1단계의 산출물이다. 교재 한 권이 저장소 안에서 어떤 폴더와 파일로 생겼는지를 정한다. 이걸 먼저 정하는 이유는 앞으로 만들 세 가지, 곧 생성 스킬과 공개 사이트와 로컬 관리 앱이 **전부 같은 폴더를 들여다보기** 때문이다. 여기가 흔들리면 셋이 각자 다른 곳을 찾게 되고 나중에 세 군데를 동시에 고쳐야 한다.

---

## 지금은 교재가 네 군데에 흩어져 있다

무에서 설계하지 않고 현행 저장소를 먼저 조사했다. 결과는 예상보다 나빴다.

| 자리 | 경로 | 무엇인가 |
| --- | --- | --- |
| 1 | `apps/agent/runs/<실행ID>/` | 옛 13단계 실행기가 남긴 단계별 증거 파일 |
| 2 | `apps/agent/generated/<슬러그>/content/` | 1을 조립한 중간 산출물 |
| 3 | `apps/portal/content/courses/<슬러그>/` | **웹 앱이 실제로 읽는 유일한 자리** |
| 4 | `apps/portal/public/courses/<슬러그>/` | 음성과 영상 원본 파일 |

`wiki/` 폴더는 교재 본문이 아니라 프로젝트 진행 상태를 적어 두는 자리였다. 교재 아홉 권 중 어떤 것은 1과 2에만 있어 학생에게 노출된 적이 없고, 어떤 것은 3에만 있다. 같은 이름의 파일이 두 자리에 있으면서 **내용이 갈라진 것도 있었다.** 검토 결과를 담은 파일 하나는 한쪽에서만 "해결됨"으로 바뀌고 다른 쪽은 옛 상태로 남아 있었다.

### 가장 큰 발견

**기계 검사가 결과를 파일로 남기지 않는다.** 정적 검사와 구조 검사 스크립트는 판정을 화면에만 출력하고 끝난다. 그래서 나중에 "이 교재가 기계 검사를 통과했는가"를 물으면 답할 근거가 저장소에 없다.

이것이 기획서가 지적한 "게이트가 실제로는 막지 못하고 참고용으로만 도는 상태"의 실체다. 판정이 남지 않으니 발행을 막을 수가 없다. 이번 배치에서 **기계 검사 결과 파일을 신설**하는 이유다.

---

## 전제로 삼은 것

기획서는 교재를 **섹션 하나의 층**으로 말하는데 현행 코드는 **챕터와 소단원 두 층**이다. 어느 쪽으로 갈지 정해야 배치가 나온다.

**두 층을 유지한다.** 근거는 둘이다. 코드와 기존 교재 아홉 권이 이미 두 층으로 되어 있어 한 층으로 접으면 전부 다시 만들어야 하고, 개요 영상을 챕터마다 하나씩 만들기로 한 결정도 두 층을 전제로 해야 수가 맞는다. 한 층으로 접으면 영상이 마흔여섯 개가 되어 감당이 되지 않는다.

따라서 **기획서가 말하는 섹션은 코드의 챕터를 가리킨다.** 임계치의 섹션 수 상한 열다섯도 챕터 기준이다. 기획서 쪽 용어 정리는 별도 작업으로 남긴다.

---

## 확정한 배치

```
저장소 루트/
├─ content/
│  ├─ courses/
│  │  └─ <교재-슬러그>/
│  │     ├─ course.json                교재 정보 파일. 이 교재의 정본
│  │     ├─ chapters/
│  │     │  └─ <NN-챕터슬러그>/
│  │     │     └─ <NN>.mdx             소단원 본문 하나당 파일 하나
│  │     └─ review/                    공개 사이트에 실리지 않는 것들
│  │        ├─ progress.json           진행 상태
│  │        ├─ machine-check.json      기계 검사 결과 (신설)
│  │        ├─ sentence-review.json    문장 단위 격리 검수 기록
│  │        ├─ section-review.json     섹션 전체 검수 기록
│  │        ├─ manual-review.json      수동 검토 목록과 처리 상태
│  │        ├─ rubric.json             이 교재의 채점 기준
│  │        └─ source-map.json         출처 목록
│  └─ standards/                       모든 교재가 함께 쓰는 기준
│     ├─ review-protocol.md            검수 프로토콜
│     ├─ beginner-baseline.md          초보자 기준
│     ├─ scoring-rules.md              채점 기준
│     ├─ manual-review-items.md        수동 검토 항목
│     ├─ thresholds.json               운영 임계치
│     └─ styles/
│        ├─ active.json                지금 활성인 스타일 버전을 가리킨다
│        └─ v1.json                    스타일 버전 하나당 파일 하나
└─ ops/
   └─ runs/
      └─ <작업ID>.json                 생성 작업 요약 기록
```

### 왜 저장소 루트의 `content/`인가

지금은 교재가 `apps/portal/content/` 안에 있다. 웹 앱의 폴더 안이다. 그러면 생성 스킬과 로컬 관리 앱이 **웹 앱의 속살을 헤집고 들어가야** 교재를 읽을 수 있다.

셋이 대등하게 같은 것을 보게 하려면 교재가 셋 중 누구의 것도 아닌 자리에 있어야 한다. 그래서 저장소 루트로 올린다. 웹 앱 쪽은 읽는 경로를 한 줄 바꾸면 된다.

### 왜 `review/` 폴더로 갈라 두는가

기획서는 "공개 대상과 비공개 대상의 파일은 **경로로 구분**한다"고 정했다. 파일 이름으로 거르는 방법도 있지만 그건 위험하다. 새 검수 파일을 하나 추가할 때마다 제외 목록을 같이 고쳐야 하고, 한 번 빠뜨리면 조용히 공개 사이트로 새어 나간다.

경로로 가르면 **기본값이 안전하다.** 빌드는 `course.json`과 `chapters/`만 가져가고 나머지는 쳐다보지 않는다. 새 파일을 아무리 추가해도 저절로 빠진다.

> **오해하지 말 것**: `review/`는 비밀 폴더가 아니다. 저장소가 공개이므로 누구나 볼 수 있고 그게 의도다. 기획서의 차별점이 "검수 근거가 공개 저장소에 남아 제삼자가 결과를 재현하고 검증할 수 있다"는 것이었다. 여기서 가르는 것은 **공개 여부**가 아니라 **공개 사이트에 실리는지 여부**다.

### 미디어는 저장소에 넣지 않는다

지금은 음성과 영상 원본이 `apps/portal/public/` 안에 들어 있다. 이건 없앤다. 인포그래픽 이미지와 음성은 객체 저장소에 올리고 **본문에는 주소만 남긴다.** 저장소에 바이너리를 쌓으면 받는 사람마다 전부 내려받게 되고 무료 한도도 금세 찬다.

## 파일별 정의

### `course.json` — 교재 정보 파일

이 교재에 관한 **정본**이다. 같은 항목을 다른 파일이 중복해 갖지 않는다.

| 항목 | 뜻 | 지금 있나 |
| --- | --- | --- |
| `id` | 교재 식별자. 슬러그가 바뀌어도 변하지 않는다 | 없음, 신설 |
| `title` | 제목 | 있음 |
| `slug` | 공개 주소에 쓰는 이름. 발행 뒤 바꾸지 않는다 | 있음 |
| `topic` | 주제 | 없음, 신설 |
| `audience` | 대상 학습자 | 없음, 신설 |
| `difficulty` | 난이도 | 있음 |
| `learning_outcomes` | 학습 목표 | 있음 |
| `content_style` | 콘텐츠 스타일 | 없음, 신설 |
| `status` | 생성 중, 초안, 발행, 숨김 넷 중 하나 | 있으나 값이 다름 |
| `published_at` | 발행 확정 시각. 숨김으로 내려도 지우지 않는다 | 있음 |
| `updated_at` | 마지막 수정 시각 | 없음, 신설 |
| `style_version` | 생성에 적용한 스타일 버전 | 없음, 신설 |
| `estimated_minutes` | 예상 학습 시간 | 있음 |
| `edit_count` | 초안 등록 뒤 본문을 손대 저장한 횟수 | 없음, 신설 |
| `rewrite_after_publish_count` | 발행 뒤 내용 누락으로 다시 쓴 횟수 | 없음, 신설 |
| `chapters` | 챕터 목록과 각 챕터의 소단원 목록 | 있음 |

**상태 값이 지금과 다르다.** 코드는 `draft / peer-review / accepted / published` 넷을 쓰는데 기획서는 `생성 중 / 초안 / 발행 / 숨김`이다. 특히 **숨김이 없다.** 한 번 발행한 교재는 지우지 않고 숨김으로만 내리기로 했으므로 이 값이 반드시 필요하다.

뒤의 두 개는 지표 계산에 쓰는 계수기다. 세는 곳이 없으면 "생성 품질이 좋아지고 있는가"를 잴 방법이 없다.

### `review/machine-check.json` — 신설

기계 검사의 판정을 남긴다. **이 파일이 없으면 게이트가 발행을 막을 근거가 없다.**

담을 것은 검사 시각, 차단 항목 수, 경고 항목 수, 통과 여부, 그리고 결함마다 식별 코드와 등급과 설명과 파일 경로와 위치다. 검사 대상 파일의 지문도 함께 남긴다. 지문이 바뀌면 판정이 무효가 되기 때문이다.

### `review/progress.json`

프로젝트 상태, 세 검수의 통과 여부, 마지막 갱신 시각, 다음 할 일을 담는다.

지금은 이 정보가 `wiki/1-Projects/<제목>/CHECKPOINT.json`에 있다. 교재 폴더 밖이다. 그래서 교재 하나를 다루려면 두 군데를 열어야 하고, 교재를 옮기거나 지울 때 한쪽만 따라간다. **교재에 관한 것은 교재 폴더 안으로 모은다.**

### 나머지 검수 파일

`sentence-review.json`, `manual-review.json`, `rubric.json`, `source-map.json`은 이름과 자리를 그대로 쓴다. 이미 그 자리에서 잘 돌고 있다.

`subchapter-review.json`만 **`section-review.json`으로 이름을 바꾼다.** 기획서가 이 검수를 섹션 전체 검수라고 부르는데 파일 이름만 소단원을 가리키고 있어 읽는 사람이 헷갈린다.

## 정리해야 할 것

배치를 정하면서 드러난 문제들이다. 이번 단계에서 다 고치지는 않고 목록으로 남긴다.

| 문제 | 어떻게 할 것인가 |
| --- | --- |
| 같은 파일이 두 자리에 있고 내용이 갈라짐 | 새 배치로 옮길 때 포털 쪽을 정본으로 삼고 나머지를 버린다 |
| 채점 기준 파일의 구조가 교재마다 다름 | 새 구조로 통일하고 옛 교재는 옮길 때 변환한다 |
| 옛 실행 증거가 대문자 파일 이름을 씀 | 옛 경로를 통째로 보존만 하고 새 배치에서는 쓰지 않는다 |
| 발행이 막힌 이유를 적는 자리와 코드가 판정하는 자리가 다름 | 판정 근거를 `machine-check.json`과 `manual-review.json` 둘로만 두고, 사람이 읽는 설명은 그 안에 함께 넣는다 |
| 기존 교재 아홉 권을 새 배치로 옮기기 | 별도 작업. 새 배치가 자리 잡은 뒤에 한다 |
