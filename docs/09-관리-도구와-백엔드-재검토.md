# 2026-08-24 관리 도구 형태와 콘텐츠 저장, 백엔드 재검토

> [구현 계획](08-구현-계획.md)을 세운 직후 사용자가 세 가지를 다시 물었다. 로컬 관리 앱이 정말 필요한가, 어차피 Supabase를 쓴다면 교재 본문도 거기 넣으면 되지 않는가, 백엔드는 Fly.io가 낫지 않은가. 셋 다 착수 전에 정리해야 나중에 되돌릴 일이 없는 질문이라 여기서 판정하고 근거를 남긴다.
>
> **결론 먼저.** 관리 GUI 앱은 1차 범위에서 뺀다. 교재 본문은 데이터베이스가 아니라 저장소의 파일로 유지한다. 백엔드는 Fly.io가 아니라 Supabase를 유지한다.

---

## 하나. 로컬 관리 앱은 정말 필요한가

### 관리 앱이 하기로 했던 일을 다시 보면

[화면 구조](04-화면-구조.md)의 화면 6~14가 하는 일은 결국 전부 **파일을 읽어 보여 주고, 파일을 고쳐 쓰는 것**이다. [아키텍처 결정](03-아키텍처-결정.md) 스스로 그렇게 적었다. "교재와 운영 상태가 모두 저장소의 파일이 된 이상 관리 도구가 하는 일은 파일을 읽고 쓰는 것뿐이다."

그리고 발행을 막는 강제력은 처음부터 GUI에 있지 않았다. 강제력은 `canPublish` 판정 함수와 공개 빌드에 있고, GUI의 발행 버튼은 그 함수를 부르는 여러 입구 중 하나였을 뿐이다. **버튼을 빼도 게이트는 그대로다.**

### 관리자가 누구인지가 판정을 가른다

[무엇을 만드는가](01-무엇을-만드는가.md)의 정의상 관리자는 "코딩 AI 에이전트와 생성 도구를 로컬에서 운영할 수 있고 공개 저장소에 쓸 수 있는 사람"이다. 즉 이 제품의 관리자는 **정의상 터미널과 에이전트를 쓰는 사람**이고, 생성·검수·발행 흐름은 어차피 에이전트 명령으로 돌아간다. 그 사람에게 아홉 화면짜리 GUI는 같은 파일을 다르게 보여 주는 두 번째 창이다.

아홉 화면은 이 계획에서 가장 큰 단일 UI 작업 덩어리였고, 콘텐츠 계약이 바뀔 때마다 같이 고쳐야 하는 코드이며, 인수인계 때 후임자가 읽어야 할 분량이다. 이 프로젝트가 Supabase를 고를 때 쓴 논리를 여기에도 적용해야 한다. **손으로 짠 코드는 곧 인수인계 부담이다.**

### 관제와 관측은 다른 문제다

GUI를 빼기로 하고 나서 한 가지를 분명히 갈라야 했다. **상태를 바꾸는 일(관제)** 은 명령으로 충분하지만, **무엇이 있고 무엇이 진행 중이고 무엇이 끝났는지를 보는 일(관측)** 은 명령을 기억해 실행해야만 보인다면 결국 아무도 안 보게 된다. 만든 교재들의 목록, 지금 돌고 있는 작업, 다음에 할 일이 한 자리에 늘 보여야 프로젝트가 머릿속에 잡힌다.

그래서 관측은 화면이 아니라 **구조**로 푼다. Vault의 프로젝트 허브가 하던 방식이고, v1 스킬이 wiki의 Hub와 INDEX를 스크립트로 자동 동기화하던 바로 그 패턴을 저장소 안으로 옮겨 오는 것이다.

- **`ops/STATUS.md` — 자동 생성 상태 보드.** 교재별 상태와 세 검수 통과 여부, 진행 중인 작업, 최근 실행 결과, 다음 할 일을 담은 한 장짜리 보드다. 스킬과 운영 CLI가 **중요한 변경을 만들 때마다 다시 생성**하며, 사람이 직접 고치지 않는다. 파일이므로 편집기에서도, GitHub 웹에서도, 밀어 넣은 뒤라면 어디서든 보인다
- **루트 `CLAUDE.md` — 에이전트 하네스.** 어떤 에이전트 세션이든 STATUS.md를 먼저 읽고 상태 요약부터 보이도록 지시한다. 폴더 구조와 명령의 지도를 함께 담아, 세션이 바뀌어도 프로젝트가 늘 같은 자리에서 시작되게 한다

### 결정: GUI 앱을 만들지 않고 네 가지로 갈음한다

| 갈음 수단 | 무엇을 대신하나 |
| --- | --- |
| **상태 보드** (`ops/STATUS.md` 자동 생성 + 루트 `CLAUDE.md`) | 화면 6의 대시보드 역할. 무엇이 있고 무엇이 돌고 있고 무엇이 끝났는지 |
| **생성 스킬의 명령** (기존 계획대로) | 생성, 검수 실행, 발행·숨김, 매 세션 시작 시 상태 요약 |
| **운영 CLI** (`status`, `metrics`, 수동 검토 기록, 예외 승인, 미디어 자산, 스타일 버전, 동기화 상태) | 화면 6, 7, 10, 11, 12, 13, 14의 기능 |
| **공개 사이트의 로컬 미리보기 모드** (초안·숨김을 배너와 함께 표시, 로컬 실행에서만) | 화면 8의 편집 확인과 화면 9 미리보기 |

본문 편집 자체는 관리자의 편집기(또는 에이전트)가 한다. 편집 후 무효화 안내 — "몇 개의 판정이 무효가 되었고 어디부터 다시 검수해야 하는가" — 는 화면이 아니라 **검수 도구가 계산해 알려 주는 값**이므로 CLI와 스킬이 그대로 제공한다.

상태 보드가 믿을 수 있으려면 **보드가 실제 상태와 어긋난 채 남는 일이 없어야 한다.** 그래서 보드 재생성을 사람의 습관이 아니라 도구의 의무로 두고, CI가 "보드를 다시 생성해도 차이가 없는가"를 검사해 낡은 보드를 잡는다.

### 무엇을 잃고, 언제 되살리나

잃는 것은 하나다. **터미널을 쓰지 않는 사람은 관리에 참여할 수 없다.** 지금은 관리자 정의상 문제가 아니지만, 비개발자 관리자(예: 조교)가 검토에 참여하게 되는 날에는 GUI가 필요해진다. 그날이 오면 화면 6~14의 기능 목록이 이미 [화면 구조](04-화면-구조.md)에 요구사항으로 남아 있으므로 그 위에 만들면 된다. 데이터가 전부 파일이라 GUI는 언제 붙여도 추가일 뿐 구조 변경이 아니다.

## 둘. 교재 본문을 Supabase에 넣으면 안 되나

"어차피 Supabase 계정이 생기는데 본문도 거기 넣으면 저장소 관리가 단순해지지 않나"라는 질문이다. 자연스러운 질문이지만, 이 제품에서는 파일 쪽이 명확히 이긴다. [아키텍처 결정](03-아키텍처-결정.md)이 Firestore를 상대로 내렸던 판정과 같은 판정이며, 상대가 Supabase Postgres로 바뀌어도 근거가 전부 유효하다.

| 기준 | 저장소의 파일 | Supabase Postgres |
| --- | --- | --- |
| 검수 무효화 판정 | 커밋과 파일 지문이 공짜로 제공 | 버전 스냅숏, 해시, 판정-내용 연결을 전부 손으로 설계 |
| 논문 재현성 | 저장소 링크 하나로 본문과 검수 근거 전문 공개 | 제삼자가 검증하려면 내보내기 도구부터 만들어야 함 |
| 교재 열람의 생존성 | 정적 파일이라 백엔드가 죽어도 읽힘 | 무료 요금제는 7일 비활동 시 정지. 교재가 백엔드 운명에 묶임 |
| 관리 권한 모델 | 저장소 쓰기 권한이 곧 관리 권한 | 서비스 키, 역할, 관리자 인증 체계가 새로 필요 |
| 코딩 에이전트 작업성 | 에이전트가 파일을 직접 생성·수정·비교 | 모든 생성·검수 단계가 API 호출을 거침 |
| 이탈 비용 | 어디로든 옮길 수 있는 평범한 파일 | [운영 위험 점검](06-운영과-인수인계-위험.md)이 넷 중 가장 높다고 판정한 사업자에 정본을 얹음 |

결정적인 것은 셋째 줄이다. 본문을 데이터베이스에 두면 공개 사이트가 실행 시점에 데이터베이스를 읽거나(정적 사이트 포기, 교재 열람이 서버 가용성에 묶임), 빌드 시점에 읽어 정적으로 굽거나(그러면 파일 대비 얻는 것이 없고 움직이는 부품만 하나 늘어남) 둘 중 하나가 된다. 이 시스템의 가장 큰 미덕 — "챗봇이 죽어도 교재는 그대로 읽힌다" — 를 스스로 허무는 구조다.

관리 GUI를 빼기로 한 이상 이 판정은 더 굳어진다. 유일한 관리 경로가 코딩 에이전트인데, 에이전트에게 가장 자연스러운 작업 대상은 API 뒤의 행이 아니라 파일이다.

데이터베이스가 이기는 조건도 적어 둔다. 비개발 편집자 여럿의 동시 실시간 편집, 사용자별로 달라지는 콘텐츠, 대규모 코퍼스 검색 같은 요구가 생기면 그때는 저울이 기운다. 지금 이 제품에는 셋 다 없다.

## 셋. 백엔드는 Fly.io가 낫지 않나

백엔드가 해야 하는 일부터 다시 세운다. 모델 열쇠 감추기, Google 로그인, 사용자별·전체 이중 한도의 원자적 검증, 대화 3일 보관, 남의 대화를 못 보게 하는 행 단위 접근 제어, 그리고 [아키텍처 결정](03-아키텍처-결정.md)이 가장 무겁게 친 기준인 **손으로 짜는 코드 최소화**다.

### 2026-08-24에 확인한 사실

- **Fly.io는 신규 계정에 무료 티어가 없다.** 2024년 10월부터 종량제 전용이 되었고, 신규 가입은 30일 시한의 5달러 체험 크레딧뿐이다. 기계 한 대 최저가가 월 2달러 수준이고 실사용 앱은 월 8~25달러대로 추산된다
- **서울 리전이 없다.** 가장 가까운 곳이 도쿄(nrt)다. 계정 정보를 국내에 두는 [개인정보 감사](07-개인정보와-보안.md)의 이점이 사라진다
- 인증이 딸려 오지 않는다. Google OAuth 흐름, 세션, 사용자 테이블, 한도 테이블, 행 단위 접근 제어를 **전부 직접 짠다.** 컨테이너와 데이터베이스 운영도 직접 맡는다

즉 Fly.io는 [아키텍처 결정](03-아키텍처-결정.md)이 이미 기각한 "직접 만드는 안"에 **유료 호스팅을 얹은 것**이다. 그 안이 기각된 이유(손으로 짠 코드가 곧 인수인계 부담)는 그대로이고, 무료라는 유일한 장점마저 없다.

### 그래서 Supabase 유지, 단 약점은 눈 뜨고 안고 간다

Supabase의 알려진 약점 두 가지는 재확인했고, 완화책이 이미 계획에 있다.

- **7일 비활동 시 무료 프로젝트 정지** (정지 전 메일 예고, 하루 한 번 요청이면 유지): keep-alive 핑을 10단계에서 만들고, "링크가 밖으로 나가는 날 이전 유료 전환" 규칙이 [운영 위험 점검](06-운영과-인수인계-위험.md)에 있다
- **이탈 비용이 넷 중 가장 높다**: 반기 약관 점검 루틴으로 감시한다

차선책도 이름을 남겨 둔다. Supabase의 약관이나 무료 한도가 흔들리는 날이 오면, 다음 후보는 Fly.io가 아니라 **Cloudflare Workers Functions + D1**이다. 이미 쓰는 사업자라 계정이 늘지 않고, 무료 한도가 넉넉하며, 비활동 정지가 없다. 대가는 인증을 손으로 짜는 것이므로, 그 날이 오기 전에는 택하지 않는다.
