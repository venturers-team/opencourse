# 저장소 충돌 해결 절차 (docs/06의 남은 항목, 구현 계획 11단계)

관리 도구는 잠금을 두지 않는다 — 충돌은 git이 처리하고, 이 문서는 후임자가 git 충돌에 익숙하지 않아도 안전하게 푸는 최소 절차다. 원칙 하나만 기억하면 된다: **콘텐츠 파일은 손으로 병합하지 않고, 도구가 다시 만들 수 있는 쪽을 버린다.**

## 파일 종류별 규칙

| 충돌 난 파일 | 해결 |
| --- | --- |
| `chapters/**/*.mdx` (본문) | 사람이 병합해도 되는 유일한 부류. 병합 뒤 **반드시** `pnpm check <슬러그>` — 본문이 바뀌면 문장 검수 지문이 깨지는 것이 정상이며, 검수를 다시 돈다 |
| `review/*.json` (검수 기록) | 손 병합 금지 (계약 위반). 본문 쪽 해결을 먼저 정하고, 검수는 세션 도구로 다시 만든다 — 지문이 어차피 무효다 |
| `course.json` | 구조(챕터 목록) 충돌이면 최신 의도 쪽을 통째로 택하고 기계 검사 재실행. `status`·`updated_at` 충돌이면 `pnpm course status`로 실제 상태를 확인하고 게이트 명령(`publish`/`hide`)으로 다시 전이한다 — 값을 손으로 고르지 않는다 |
| `media.json` | 두 쪽 모두 실재하는 업로드 기록이면 항목을 합집합으로 합치되, 교체 관계면 옛 항목을 `cleanup`으로. 합친 뒤 `pnpm ops media` 목록으로 검산 |
| `ops/STATUS.md` | 아무 쪽이나 택해도 된다 — `pnpm board`가 다시 만들고 `board:check`가 검증한다 |
| `ops/runs/*` | 실행 기록은 불변 — 양쪽 다 남긴다 (파일명이 run_id라 실제 충돌은 거의 없다) |
| 코드·문서 | 일반 git 병합. 끝나면 `pnpm typecheck && pnpm test` |

## 절차

```bash
git pull --rebase          # 1. 충돌 발생
git status                 # 2. 충돌 파일 목록 확인 → 위 표에서 부류 찾기
# 3. 표의 규칙대로 해결 (재생성 가능한 것은 도구로 재생성)
pnpm board && pnpm check <슬러그>   # 4. 보드·게이트 재검
git add -A && git rebase --continue
pnpm test && pnpm e2e      # 5. 전체 검증 뒤 푸시
```

막히면 `git rebase --abort`로 원상 복구하고 다시 시작한다 — 저장소가 진실이므로 잃는 것이 없다.
