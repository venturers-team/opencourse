# 생성 파이프라인

> [화면 구조](04-화면-구조.md)의 명령 흐름(S1~S17)을 실제 생성 단계로 구체화한다. v1 실행기의 13단계 구성에서 단계 배치와 산출물 계약을 가져오되, v2의 저장소 배치와 게이트 위에 다시 얹는다. [구현 계획](08-구현-계획.md) 3단계(생성 스킬)의 설계 입력이며, 콘텐츠 품질이 게이트에 도달하기 **전에** 어디서 만들어지는지를 정한다.

---

## 원칙 넷

1. **품질은 앞에서 넣고 뒤에서 거른다.** 게이트는 마지막 그물이지 품질의 원천이 아니다. 스타일 버전(문체·톤·용어 규칙), 초보자 기준, 교재별 루브릭, 챕터별 작성 지시문이 생성의 **입력**으로 먼저 들어간다. 걸러서 좋아지는 글보다 처음부터 잘 쓰인 글이 싸다.
2. **모든 단계는 파일을 남긴다.** 단계마다 정해진 산출물이 있고, 실패하면 그 단계부터 재개한다. 처음부터 다시 돌리는 일이 없어야 큰 교재도 끝까지 간다. 단계별 소요 시간은 `ops/runs/`에 쌓인다.
3. **전부 아니면 무.** 필수 산출물이 하나라도 실패하면 어느 것도 초안으로 등록되지 않는다. 반쯤 만들어진 교재가 초안 자격으로 굴러다니는 상태가 가장 나쁘다.
4. **결함의 계급은 구조로 막는다.** 소단원 단위로 생성하되 문맥은 **앞 챕터의 확정 요약만** 준다(섹션 순서 역전이 구조적으로 어려워진다). 출처 인용은 `source-map.json`에 등록된 항목만 허용한다(지어낸 출처가 조용히 스며들지 못한다). 챕터 3000자·영상 90초 상한은 임계치 파일이 강제한다.

## 미디어와 저장소의 순서

미디어가 저장소보다 **먼저** 존재해야 한다. 저장소의 본문에는 주소만 실리므로, 그 주소가 아직 없는 커밋은 깨진 교재를 만든다.

```
로컬 렌더 → 로컬 검증 → R2 업로드 → URL 수신 → URL 응답 확인
→ 미디어 목록에 URL 기록 (본문은 식별자로 참조) → 커밋 → 푸시 → 자동 빌드 → 공개
```

- **저장소에는 이미 R2에 존재하는 주소만 커밋된다.** 업로드가 실패하면 초안 등록도 실패한다
- 업로드는 챕터마다 하지 않고 **모든 미디어가 로컬에서 완성·검증된 뒤 한 번에** 한다. 도중에 죽은 작업이 R2에 고아 자산을 남기지 않게 하기 위해서다
- 교체된 자산은 지우지 않고 정리 대상으로 표시한다. 90일 뒤 삭제, 발행 교재가 참조하는 것은 보호 ([화면 구조](04-화면-구조.md) 화면 12 규칙)
- 인프라 연결(9단계) 전 로컬 개발 중에는 업로더가 로컬 폴더 백엔드로 돈다. 인터페이스는 같다

## 열두 단계

본문과 미디어 단계(S6~S10)는 **챕터 단위로 반복**하며, 실패하면 실패한 챕터의 실패한 단계부터 재개한다.

| 단계 | 이름 | 주 산출물 | v1 대응 |
| --- | --- | --- | --- |
| S1 | 프로젝트 생성 | `course.json` 뼈대 (상태: 생성 중), 실행 기록 시작 | — |
| S2 | 자료 수집 | `review/source-map.json` — 출처마다 주소·확인 시각·사용 조건 | collect |
| S3 | 목차 제안과 승인 | `course.json`의 챕터·소단원 구조와 챕터 의존 관계. **사람이 승인해야 진행** | map |
| S4 | 실행 전 점검 | 임계치 5종 비교와 예상 시간. 초과 시 분할·보류 안내 | 신설 |
| S5 | 루브릭과 작성 지시문 | `review/rubric.json`, 챕터별 작성 지시문 | pedagogy + plan |
| S6 | 본문 초안 | `chapters/<NN>/<NN>.mdx` — 소단원당 모델 호출 1회 | draft |
| S7 | 인포그래픽 | 챕터별 HTML 저작 → Playwright PNG 렌더 + **대체 설명** (로컬) | figures |
| S8 | 영상 대본 | 장면 목록 — 장면마다 시각 정의 + 나레이션 한 문장 | visuals + animate |
| S9 | 음성 합성과 검증 | 장면별 TTS mp3 + Whisper 재전사 검증 (로컬) | narrate |
| S10 | 타임라인 조립 | `timeline.json` + 챕터 mp3 + vtt 자막 (로컬) | compose |
| S11 | 미디어 일괄 업로드 | R2 업로드, URL 응답 확인, 미디어 목록에 URL 기록 | 신설 |
| S12 | 초안 등록과 기계 검사 | 상태: 초안 (전부 아니면 무), `machine-check.json` 자동 1회 | verify의 후신 |

이후는 [검수 게이트](05-검수-게이트.md)의 영역이다: 문장 격리 검수 → 섹션 검수 → 수동 검토 → 발행.

**v1에서 버린 것**: `enrich`(외부 미디어 자동 큐레이션)는 1차 범위에서 뺀다. `build`(포털 변환)는 단계가 아니라 정적 사이트의 상시 빌드가 맡는다. `animate`의 MP4 렌더는 브라우저 조립으로 대체되어 사라졌다.

### 왜 검수가 업로드와 초안 등록 뒤에 오는가

"검수를 통과한 것만 올리고 등록해야 하지 않나"라는 질문이 자연스럽게 나온다. 순서가 이런 데는 세 가지 이유가 있다.

1. **게이트는 초안의 관문이 아니라 발행의 관문이다.** 초안은 공개 빌드에 실리지 않으므로 미검수 초안이 존재해도 위험이 없다. 등록 전에 검수를 요구하면 검수에 걸린 교재가 어떤 상태로도 존재하지 못해 보드·미리보기·CLI 어디에서도 보이지 않게 된다.
2. **검수한 것과 발행되는 것이 같아야 한다.** 수동 검토는 사람이 미리보기에서 실제 서빙될 그림과 음성을 보고 들어야 하고("이미지가 본문과 맞는가"), URL이 실제로 응답하는지까지 확인된 최종본이어야 "검수한 그것이 그대로 발행된다"가 성립한다. 발행 직전에 업로드하면 검수가 본 것과 학습자가 받는 것이 다른 경로가 된다.
3. **검수는 루프이고, 그 작업대가 초안 상태다.** 수정 → 무효화 → 재검수를 최대 6회 도는 동안 교재는 초안으로 존재해야 한다. 발행 직전 업로드 방식은 그 며칠 동안 미디어를 관리자 기기 한 대에만 남겨 둔다 — 기기가 고장 나면 전부 재생성이고, 다른 기기에서는 미리보기가 되지 않는다.

다만 싼 검사까지 뒤로 미루는 것은 아니다. 출처 3요소(S2), 대체 설명(S7), Whisper 검증(S9)은 생성 단계 안에 박혀 즉시 실패를 내고, 기계 검사는 등록 즉시(S12) 자동으로 돈다. 뒤로 가는 것은 비싼 LLM 검수뿐이다.

### 기각된 초안의 미디어는 어떻게 되나

지우지 않는다. 검수에 걸린 초안은 대개 고쳐서 다시 도는 것이므로 미디어는 다음 회차에서 그대로 쓰인다. 본문 수정으로 미디어가 교체되면 옛 자산은 자동으로 **정리 대상 표시**가 붙고 90일 뒤 삭제된다(관리자가 즉시 지울 수도, 표시를 취소할 수도 있다). 발행 교재가 참조하는 자산은 보호된다 — [화면 구조](04-화면-구조.md) 화면 12의 규칙 그대로다. 영구 폐기된 교재의 자산도 같은 경로로 청소된다.

이 잔류의 비용은 저장뿐이다. R2는 송신 무과금이고 교재 한 권의 미디어가 약 70MB로 무료 한도 10GB의 0.7%다. 발행 직전 업로드로 바꾸면 절약되는 것은 영구 폐기된 초안의 저장 용량뿐인데, 대가로 발행 순간이 업로드→기록→확인→푸시의 다단계 트랜잭션이 되어 가장 민감한 자리에 실패 지점이 생긴다. 지금 설계는 위험한 작업을 일찍 끝내고 발행을 "상태 한 줄 바꿔 푸시"로 남겨 둔다.

**이 질문이 계약을 하나 고쳤다.** 본문이 미디어를 R2 URL로 직접 참조하면, 미디어 하나를 재업로드해 URL이 바뀔 때마다 본문이 바뀌어 문장·섹션 검수가 전부 무효가 된다. 그래서 **본문은 미디어를 안정 식별자(예: `fig-01`)로만 참조하고, 식별자→URL 매핑은 챕터 미디어 목록 파일에만 둔다.** 미디어 교체·재업로드는 산문 지문을 건드리지 않으므로 검수 판정이 살아남고, 기계 검사만(싸므로) 다시 돌리면 된다.

### 단계별로 적어 둘 것

**S2 자료 수집.** 기계 검사의 차단 항목 세 개(출처 주소·확인 시각·사용 조건 누락)가 여기서 결정된다. 수집 시점에 세 값을 함께 적지 않은 자료는 등록하지 않는다. 나중에 채우는 방식은 반드시 빈칸을 남긴다.

**S3 목차 승인.** 제안-편집-승인이 명확히 갈린다. 승인 전에는 어떤 생성도 시작되지 않고, 승인된 구조가 이후 모든 단계의 기준이 된다. 목차를 다시 고치면 S5부터 다시 돈다.

**S6 본문 초안.** 소단원 하나당 호출 한 번이고, 문맥으로 받는 것은 작성 지시문과 **앞 챕터들의 확정 요약**뿐이다. 뒤 챕터의 내용을 미리 볼 수 없으므로 "앞에서 다뤘다"는 회수가 실제 앞을 가리키게 된다. 확인하지 못한 사실은 확인하지 못했다고 그대로 적는다 — 그 문구는 기계 검사가 잡아 세운다. 스스로 속이는 것보다 걸리는 편이 낫다.

**S7 인포그래픽.** HTML은 디자인 시스템(구현 계획 7단계)의 토큰으로 저작해 교재 전체의 그림이 한 벌로 보이게 한다. 대체 설명이 없는 PNG는 산출물로 인정하지 않는다 — 기계 검사 차단 항목이기 때문이다.

**S9 음성 검증.** 합성된 음성을 Whisper로 재전사해 대본과 유사도 0.65 이상인지 확인한다. 불합격 장면은 재합성하되 상한 횟수를 두고, 넘으면 단계 실패로 기록한다. 조용히 어긋난 음성을 통과시키는 것이 최악이다. 이 검증은 "말한 대로 소리가 났는가"까지다. "본문과 같은 이야기인가"는 [수동 검토 항목](../content/standards/manual-review-items.md)에 남는다.

## 영상 워크플로

영상 파일은 **어디에도 존재하지 않는다.** 만들어지는 것은 세 가지다: 장면 시각을 정의한 `timeline.json`, 챕터당 하나로 이어 붙인 나레이션 mp3, vtt 자막. 브라우저의 Remotion Player가 셋을 읽어 재생 시점에 조립한다.

```
영상 대본 (장면 목록, 챕터당 ≤ 90초)
  └─ 장면마다: 시각 정의 + 나레이션 한 문장
      ↓ 장면별 Qwen3-TTS 합성
      ↓ Whisper 재전사 — 유사도 ≥ 0.65, 불합격은 재합성
  음성 길이 측정 → 장면 시작 시각 계산 (장면 간격 2초)
  → 챕터 mp3 하나로 연결 + vtt 자막 생성 + timeline.json 확정
      ↓
  mp3 → R2 (S11에서 일괄)         timeline.json · vtt → 저장소 (텍스트)
      ↓
  학습자 브라우저: Remotion Player가 조립 재생, 자막 표시, 준비 중 표시
```

- 나레이션 문장이 장면 단위로 원자적이므로, 한 장면의 음성만 불합격해도 그 장면만 다시 합성한다
- 자막(vtt)과 타임라인은 텍스트라 저장소에 산다. 덕분에 영상의 내용 변경도 커밋 이력에 남고, 지문 기반 무효화가 영상에도 닿는다
- 다운로드 수단은 두지 않는다. 재생 준비 중 상태 표시는 화면 요구사항([화면 구조](04-화면-구조.md) 화면 2·3)이다
- 교재 단위 개요 영상 1편도 같은 워크플로로 만든다 (구현 계획의 가정 항목)

**TTS는 Qwen3-TTS로 확정한다** (2026-08-25 사용자 확인). v1이 이미 이 도구로 합성해 왔고 이행 비용이 없다. CosyVoice 2와 Chatterbox는 S9의 검증 불합격률이나 운율 실측이 크게 나쁠 때만 검토하는 비상 대안으로 남기며, 장면 단위 합성 구조는 도구를 갈아도 그대로다.

## 모델 운용

v1의 이원화를 이식한다. 본문·영상 대본·나레이션 문장처럼 **학습자가 읽고 듣는 글**은 상급 모델이 쓰고, 구조 잡기·집계·변환처럼 **결정이 뻔한 일**은 하급 모델이나 낮은 효율로 돌린다. 문장 검수자는 이와 별개로 매번 새로 시작하는 서브에이전트다([구현 계획](08-구현-계획.md)의 가정).

| 추가 | 무엇 | 어디 |
| --- | --- | --- |
| 챕터 미디어 목록 | 식별자→R2 URL 매핑, timeline.json, vtt, 대체 설명. **본문은 미디어를 식별자로만 참조한다** | 챕터 폴더 안 |
