# 구현 계획

> 문서 01~07과 검수 기준 다섯 문서를 입력으로, **무엇을 어떤 순서로 만들고 각 단계가 끝났음을 어떻게 증명하는지**를 정한다. 이 문서는 살아 있는 계획이다. 구현 중에 틀린 것이 드러나면 계획을 고치고 맨 아래 변경 기록에 남긴다. 완료 조건을 조용히 낮추는 것만은 하지 않는다.

아키텍처와 화면과 게이트는 문서 03, 04, 05에서 이미 확정되어 있다. 이 계획을 세우면서 **2026년 8월 24일에 네 가지를 새로 정했다.**

| 결정 | 내용 |
| --- | --- |
| 저장소 구성 | 이 저장소 하나를 **단일 공개 모노레포**로 쓴다. `apps/site`(공개 사이트), `packages/`(공유 라이브러리), `skills/opencourse`(생성 스킬), `content/`, `ops/`, `docs/`가 한 저장소에 산다 |

| 챗봇 백엔드 | 재검토 결과 **Supabase 유지.** Fly.io는 무료 티어가 없고 서울 리전이 없으며 인증·한도·접근 제어를 전부 손으로 짜야 해서 기각. 차선책은 Cloudflare Workers + D1으로 기록만 해 둔다. 근거는 [재검토](09-관리-도구와-백엔드-재검토.md) |

## 무엇을 어떤 순서로 만드는가

순서에는 네 가지 원칙이 있다.

1. **계약이 먼저다.** 생성 스킬과 공개 사이트와 운영 도구가 전부 같은 폴더를 본다. 파일 구조와 스키마가 흔들리면 셋을 동시에 고쳐야 하므로, 콘텐츠 계약을 코드보다 먼저 굳힌다.
2. **게이트가 화면보다 먼저다.** 이 제품의 차별점은 검수 게이트이고, 사이트와 운영 도구는 게이트가 남긴 판정 파일을 보여 주는 쪽이다. 보여 줄 것이 먼저 있어야 한다.
3. **디자인 시스템이 화면보다 먼저다.** 디자인 리뉴얼이 결정되어 있으므로, 화면을 만들고 다시 칠하는 대신 시스템을 먼저 세우고 그 위에 화면을 올린다.
4. **서버는 맨 마지막이다.** 챗봇은 유일한 서버이자 유일한 상시 비용이다. 나머지 전부가 로컬과 정적 파일로 검증된 뒤에 붙인다.

## 단계별 계획

### 0. 저장소 부트스트랩

**만드는 것**
- `git init`과 `.gitignore`. 지금 이 폴더는 git 저장소가 아니다
- pnpm 워크스페이스, TypeScript, Node 22, 포매터와 린터
- 폴더 골격: `apps/site`, `packages/content`, `packages/ui`, `skills/opencourse`
- 루트 `CLAUDE.md` 초안: 에이전트가 세션마다 `ops/STATUS.md`를 먼저 읽고 상태 요약부터 보이게 하는 하네스. 폴더 구조와 명령의 지도. 단계가 진행될 때마다 함께 자란다
- GitHub Actions CI: 밀어 넣을 때마다 타입 검사와 테스트

**증명하는 방법**: 빈 워크스페이스에서 `pnpm install`, `pnpm build`, `pnpm test`가 전부 초록으로 끝난다. CI 설정이 로컬과 같은 명령을 돈다.

### 1. 콘텐츠 계약

문서 02의 배치를 코드가 읽고 쓰는 계약으로 굳힌다. **여기가 흔들리면 뒤의 모든 단계가 같이 흔들리므로, 이 단계의 완료 기준이 가장 엄격하다.**

**만드는 것**
- **스키마 설계는 [11 콘텐츠 계약 스키마](11-콘텐츠-계약-스키마.md)로 확정되어 있다.** 이 단계는 그 문서를 코드로 옮기는 일이며, 문서에 없는 필드를 임의로 만들지 않는다
- `packages/content`: 계약 파일 전체의 스키마와 타입 — `course.json`, `media.json`(+타임라인), `machine-check.json`, `sentence-review.json`, `section-review.json`, `manual-review.json`, `progress.json`, `rubric.json`, `source-map.json`, `thresholds.json`, 스타일 버전, `ops/runs`
- 상태 값 넷: 생성 중, 초안, 발행, 숨김
- 지문 유틸리티: 파일 내용의 해시. 검수 무효화 판정의 기준
- **`canPublish(교재폴더)` 함수 하나**: 세 검수의 통과 여부와 지문 일치와 권리 검토 잔여를 판정해 `통과 여부 + 막힌 이유 목록`을 돌려준다. 빌드도, 발행 명령도, 관리 앱 발행 버튼도 **전부 이 함수 하나를 부른다.** 판정 로직이 두 벌이 되는 순간 게이트에 다른 문이 생긴다
- 테스트용 고정 교재(fixture): 작은 2챕터 교재와 완비된 검수 파일 일습. `content/courses/`가 아니라 패키지 테스트 폴더에 둔다
- [생성 파이프라인](10-생성-파이프라인.md)이 요구하는 계약 추가분: 챕터 미디어 목록(식별자→URL 매핑·timeline·vtt·대체 설명)과 실행 중간 산출물 폴더(`ops/runs/<작업ID>/`)의 파일명과 스키마. **본문은 미디어를 안정 식별자로만 참조한다** — 미디어 재업로드가 산문 지문과 검수 판정을 건드리지 않게 하기 위해서다

**증명하는 방법**
- 스키마 테스트: 고정 교재는 통과하고, 필수 항목을 하나씩 지운 변형은 전부 거부된다
- `canPublish` 진리표 테스트: 검수 파일 없음 / 실패 / 지문 불일치 / 권리 검토 잔여 / 전부 정상 — 각 조합에서 판정과 이유가 맞다
- 지문 테스트: 같은 내용은 같은 지문, 한 글자 수정은 다른 지문

### 2. 기계 검사

v1의 `course-static-check.mjs`와 `course-structure-check.mjs`의 **판정 로직을 가져와** 새 계약 위에 다시 얹는다. v1의 가장 큰 구멍이었던 "판정을 화면에만 출력하고 파일로 남기지 않는" 문제를 여기서 닫는다.

**만드는 것**
- [채점 기준](../content/standards/scoring-rules.md)의 정적 검사 11항목과 구조 검사 6항목 전부
- 두 검사를 **항상 함께 실행하고 결과를 하나로 합쳐** `review/machine-check.json`에 쓴다: 검사 시각, 차단·경고 수, 통과 여부, 결함별 코드·등급·설명·위치, 검사 대상 파일의 지문
- 실행 명령: `pnpm check <슬러그>`

**증명하는 방법**
- 항목별 테스트: 17개 규칙 각각에 대해 걸리는 고정 교재와 통과하는 고정 교재가 최소 하나씩 있다. v1의 테스트를 이식해 출발점으로 쓴다
- 같은 입력에 두 번 돌리면 같은 판정이 나온다
- 검사 후 본문을 고치면 지문 불일치로 `canPublish`가 판정을 무효로 본다

### 3. 생성 스킬

로컬 에이전트 명령 흐름(문서 04의 S1~S17)을 `skills/opencourse`로 만든다. v1 스킬의 **단계 구성과 수명주기 로직**을 가져오되, wiki와 CHECKPOINT 기반 상태 관리는 버리고 `review/progress.json`과 `ops/runs/`로 대체한다. **단계 구성의 상세 설계는 [생성 파이프라인](10-생성-파이프라인.md)에 있다** — 열두 단계, 챕터 단위 반복과 재개, 미디어 일괄 업로드 순서, 영상 워크플로.

**만드는 것**
- 프로젝트 수명주기: 새로 만들기, 상태 보기, 다음 할 일 안내. 매 단계에서 지금 어디인지·다음에 무엇이 가능한지·무엇을 권하는지 세 가지를 보인다
- 실행 전 점검: `thresholds.json`의 다섯 값을 재고 하나라도 넘으면 시작하지 않는다. 파일이 없으면 기본값으로 돌되 그 사실을 알린다
- 목차 제안 → 편집 → 승인 → 생성 실행: 소단원별 MDX 본문, 인포그래픽 HTML, 나레이션 대본, 영상 타임라인 JSON
- 미디어 렌더: Playwright로 HTML→PNG, Qwen3-TTS로 음성, Whisper 재전사 유사도 0.65 검증
- 미디어 업로더: 인터페이스 하나에 로컬 저장 백엔드(개발용)와 R2 백엔드(9단계에서 연결) 두 구현. 본문에는 주소만 남는다
- **전부 아니면 무:** 필수 결과물이 하나라도 실패하면 어느 것도 초안으로 등록되지 않는다
- `ops/runs/<작업ID>.json`: 시작·종료 시각, 단계별 소요 시간, 마지막 상태, 실패한 단계 이름

**증명하는 방법**
- 수명주기와 실행 전 점검의 단위 테스트. 임계치 하나를 초과시킨 입력이 실제로 보류된다
- 작은 시험 주제로 로컬에서 끝까지 한 번 돌려 초안 등록까지 간다
- 단계 하나를 고의로 실패시키면 초안이 등록되지 않고, 실행 기록에 실패한 단계와 시간이 남는다

### 4. 문장 검수와 섹션 검수

v1 `sentence-review.mjs`(934줄)와 `subchapter-review.mjs`의 판정 로직을 가져와 [검수 프로토콜](../content/standards/review-protocol.md)의 규칙대로 다시 얹는다. 검수자는 로컬 코딩 에이전트가 **매번 새로 시작하는 서브에이전트 실행**이다. 별도 API 열쇠가 필요 없고, 실행 식별자와 모델 식별자가 격리 증거로 남는다.

**만드는 것**
- 문장 추출: 학습자가 보게 될 단위만. 코드 블록과 머리말 제외
- 격리 실행기: 검수자에게 문장 하나와 학습자 상태만 넘긴다. 다섯 차원 0·1·2점, 판정표로 등급 확정
- 학습자 상태 장부: 상한(40·40·20)과 초과 시 버림 기록
- 기록 거부 규칙: 격리 증거가 없거나, 문제 목록 없는 중대·심각이거나, 판정표와 어긋난 등급은 **기록하지 않는다**
- 무효화: 문장 수정은 그 문장부터 뒤 전부, 앞 섹션 수정은 그 섹션부터 뒤 전부, 프로토콜·초보자 기준의 지문 변경은 전체. 회차 상한 6회, 이전 지문으로 되돌아오면 정지
- 섹션 검수: 섹션 본문 전체와 앞 섹션까지의 확정 내용을 주고 다섯 차원(완결성, 순서, 틀 일관성, 근거, 학습자 도달 상태)으로 판정. **v1과 달리 결과가 게이트에 연결된다**
- 예외 승인: 문장·섹션 검수의 심각 등급만, 사유와 승인자를 남기고, 누적 건수를 교재에 표시

**증명하는 방법**
- 오케스트레이션 로직은 **결정적 가짜 검수자**로 테스트한다: 무효화 범위, 장부 상한, 증거 누락 거부, 판정표 불일치 거부, 회차 상한, 루프 감지
- 실행기가 검수자에게 넘기는 입력에 원문 전체·이웃 문장·다른 판정이 **없다는 것을 테스트가 단언한다**
- 고정 교재에 진짜 모델로 한 번 완주하는 연기 시험

### 5. 발행 게이트

문서 05의 요구 — "상태 값을 직접 고치는 경로를 포함해 어떤 경로로도 공개되지 않는다" — 를 구조로 만든다. **막는 자리는 공개 빌드 하나다.** 빌드는 상태가 발행이면서 `canPublish`가 참인 교재만 산출물에 담는다. 상태 값만 발행으로 고쳐도 검수 증거가 없으면 빌드가 거른다. 발행 명령과 발행 버튼의 사전 확인은 편의 장치이지 방어선이 아니다.

**만드는 것**
- 빌드 파이프라인의 수집 단계: `canPublish` 통과분만 포함, 제외된 교재는 이유와 함께 빌드 로그에 보고
- 상태 전환 명령(`publish`, `hide`): 전환 전에 `canPublish`를 부르고, 막히면 이유를 그대로 보여 준다
- 발행 이력 규칙: 한 번 발행된 교재는 삭제 불가, 숨김만 가능. `published_at`은 숨겨도 지우지 않는다

**증명하는 방법 — 우회 시도 테스트 일습.** 이 테스트 묶음이 성공 기준 "검수 미통과 발행 0건"의 증거다.
- 검수 없이 상태만 발행으로 직접 수정 → 빌드 산출물에 없다
- 검수 통과 후 본문을 한 글자 수정(지문 드리프트) → 산출물에 없다
- 기계 검사의 차단 항목을 예외 승인으로 넘기려는 시도 → 거부된다
- 세 검수 통과·권리 검토 완료 → 산출물에 있다
- 숨김 처리 → 목록·사이트맵·산출물에서 사라지고, 그 주소는 없는 주소와 같은 안내를 낸다

### 6. 운영 CLI

관리 GUI 앱을 만들지 않기로 한 [재검토](09-관리-도구와-백엔드-재검토.md)의 결과다. 화면 6~14가 정의했던 기능을 명령으로 만든다. 화면 목록은 GUI 명세가 아니라 **이 단계가 충족해야 할 요구사항 목록**으로 읽는다.

**만드는 것**
- **`ops/STATUS.md` 자동 생성 상태 보드**: 교재별 상태와 세 검수 통과 여부, 진행 중인 작업, 최근 실행 결과, 다음 할 일을 담은 한 장짜리 보드. 스킬과 CLI가 중요한 변경을 만들 때마다 다시 생성하며 사람이 직접 고치지 않는다. v1이 wiki Hub와 INDEX를 스크립트로 동기화하던 패턴의 이식이다. 편집기에서도 GitHub 웹에서도 보인다 (화면 6의 대시보드 몫)
- `pnpm status`: 교재별 상태와 세 검수 통과 여부, 지문 일치, 보내지 않은 변경 건수(git 기준), 미디어 용량과 한도 비율, 월 빌드 횟수 (화면 6·14의 몫). **생성 스킬이 매 세션 시작마다 이 요약을 먼저 보여 준다** — 지표가 목표로만 적히고 측정되지 않는 상태를 막던 화면 6의 역할을 이것이 잇는다
- `pnpm metrics`: 세 지표(완료율, 오류율, 첫 초안 소요 중앙값)와 집계 기간·대상 작업 수, `ops/runs` 집계 (화면 6·13의 몫)
- 수동 검토 기록 명령: [수동 검토 항목](../content/standards/manual-review-items.md)별 처리·보류를 사유·처리자·시각과 함께 기록. **사유 없는 보류는 거부** (화면 7의 몫)
- 예외 승인 명령: 문장·섹션 검수의 심각 등급만, 사유·승인자 기록과 누적 표시 (화면 7의 몫)
- 미디어 자산 명령: 목록, 정리 대상 표시와 90일 규칙, **발행 참조 자산의 삭제 거부** (화면 12의 몫)
- 스타일 버전 명령: 목록, 새 버전 저장, 활성화, 참조 유무 표시 (화면 10의 몫)
- 검수 기준 지문 확인: 기준 문서 변경으로 무효가 된 검수가 어느 교재에 있는지 표시 (화면 11의 몫. 편집 자체는 파일을 직접 고친다)
- 편집 후 무효화 안내: 검수 도구가 저장된 파일의 지문을 비교해 **몇 개의 판정이 무효가 되었고 어디부터 다시 검수해야 하는지** 출력 (화면 8이 하려던 안내)

**증명하는 방법**
- 각 명령의 단위 테스트: 사유 없는 보류 거부, 발행 참조 자산 삭제 거부, 예외 승인의 누적 집계
- 임시 작업 복사본을 놓고 status·metrics가 실제 파일 상태와 git 상태를 정확히 반영하는지 검증
- 스킬 세션 시작 시 상태 요약이 출력되는지 확인
- **보드는 낡지 않는다**: 수명주기 동작마다 STATUS.md가 갱신되는 테스트, 그리고 CI가 "보드를 다시 생성해도 차이가 없는가"를 검사해 실제 상태와 어긋난 보드를 잡는다

### 7. 디자인 시스템

디자인 리뉴얼이 결정되어 있으므로 화면을 만들기 전에 시스템부터 세운다. **프로세스가 2026-08-25에 확정됐다**: 디자인 자체는 사용자가 Claude Design에서 만든다.

1. 입력은 [12 공개 사이트 IA](12-공개-사이트-IA.md) — 페이지·컴포넌트·상태 전수와 핸드오프 프롬프트가 이미 작성되어 있다
2. **사용자가 그 프롬프트로 Claude Design에서 디자인 시스템과 화면 시안을 만든다** (무드·레퍼런스는 사용자가 채움)
3. 결과의 토큰과 컴포넌트를 `packages/ui`로 구현한다: 색·타이포·간격 토큰, 컴포넌트, 접근성 규칙(키보드 도달, 색 대비, 색만으로 전달 금지)

**증명하는 방법**: 스타일 가이드 페이지가 IA의 컴포넌트 인벤토리를 빠짐없이 렌더한다. 키보드만으로 전 컴포넌트가 조작된다. 색 대비가 기준을 통과한다. **디자인 원본(Claude Design 결과)과 구현이 어긋나지 않는지 사용자가 보고 승인한다.**

### 8. 공개 사이트

화면 1~4를 `apps/site`에 만든다. Next.js 정적 출력(`output: 'export'`)으로, 서버 없이 파일만 내보낸다.

**만드는 것**
- 화면 1 발행 교재 목록: 검색, 대상·난이도 필터, 정렬, 빈 상태
- 화면 2 교재 상세: 목차, 학습 목표, 개요 영상, 출처 표시
- 화면 3 섹션 페이지: 챕터의 소단원들을 한 페이지로 이어 붙인 본문, 인포그래픽과 대체 설명, 섹션 개요 영상, 이전·다음 이동, 목차, 소제목 이동
- 화면 4 접근 불가 안내: 없는 주소와 숨김·초안 주소가 **구분되지 않는** 같은 안내
- 개요 영상: Remotion Player가 타임라인 JSON과 음성 주소를 받아 브라우저에서 조립. 준비 중 표시, 다운로드 수단 없음. v1의 조립 로직을 참고하되 화면은 새 디자인 시스템으로
- `sitemap.xml`, `robots.txt`: 발행 교재만
- 챗봇 문맥 번들: 발행 교재의 섹션 본문을 산출물에 함께 담는다. 10단계에서 챗봇이 읽을 유일한 자료다
- **로컬 미리보기 모드** (화면 9의 몫): 로컬 실행에서만 초안·숨김 교재를 미리보기 표시와 함께 보여 준다. 정적 출력 경로에서는 이 모드가 **구조적으로 꺼진다** — 산출물 수집은 언제나 `canPublish`를 거친다

**증명하는 방법**
- 고정 교재를 발행 상태로 빌드해 Playwright E2E: 목록→상세→섹션 이동, 검색·필터 동작, 영상 플레이어 마운트, 키보드만으로 전 조작 도달, 404 무구분, 사이트맵에 발행분만
- 정적 산출물을 단순 파일 서버로 띄워도 전부 동작한다(서버 의존 없음의 증명)
- **미리보기 모드를 켠 채 정적 출력을 시도해도 초안이 산출물에 들어가지 않는다**는 테스트

### 10. 챗봇

화면 5와 유일한 서버. 문서 07의 감사 결과를 설계 입력으로 쓴다.

**만드는 것**
- Supabase 프로젝트: **생성 시점에 서울(ap-northeast-2) 확인** — 되돌릴 수 없는 값
- Google 로그인(Supabase Auth), 대화·사용량 테이블, `auth.uid() = user_id` RLS, 계정 삭제 시 연쇄 삭제(`ON DELETE CASCADE`), 대화 3일 자동 삭제 배치
- Edge Function: 세션 검증 → **모델 호출 전에** Postgres 원자적 카운터로 사용자별·전체 이중 한도 확인 → OpenRouter 호출. ZDR을 계정 설정과 요청 파라미터 양쪽에서 강제
- 문맥은 7단계의 챗봇 문맥 번들(공개 산출물)만 읽는다. 저장소 접근 경로 자체가 없다
- 시스템 지시와 사용자 입력 분리, 문맥 이탈 요청 1차 필터
- 부유형 패널: 기본 닫힘, 열기 전 서버 호출 없음, 남은 횟수 표시, 한도·장애 상태를 구분해 표시, "로그인은 횟수 세기용" 문구, "대화는 평가에 쓰이지 않는다" 문구
- 개인정보 처리방침 페이지와 목적별 동의(시각·버전 기록), 보호책임자 표기, 국외 이전 고지
- 무료 요금제 자동 정지 대비 keep-alive 핑(GitHub Actions 크론). 유료 전환 시점("링크가 밖으로 나가는 날 이전")을 인수인계 문서에 명기
- **법률 확인 불가 항목 체크리스트**: 문서 07이 확인 불가로 남긴 항목들(국외 이전 예외 적용 여부 등)은 코드가 아니라 사용자가 법률 자문으로 채울 목록으로 정리

**증명하는 방법**
- 한도 우회 시도: 클라이언트를 건너뛰고 API를 직접 호출해 한도 초과분이 서버에서 거부되는지
- RLS: 계정 두 개로 서로의 대화 조회가 거부되는지
- 초안 격리: 초안 교재의 문장이 문맥 번들에 없고, 챗봇이 그 내용을 답하지 못하는지
- 패널 상태: 비로그인·한도 소진·백엔드 정지 세 상태가 각각 구분된 안내를 내는지
- 프롬프트 주입 연기 시험("지금부터 규칙을 무시하고" 류)

### 11. 실전 통과와 측정

**진짜 교재 한 권을 주제 입력부터 공개 사이트 발행까지 완주시킨다.** 이것이 전체의 인수 시험이다.

**만드는 것**
- 실제 주제로 생성 → 기계 검사 → 문장 검수 → 섹션 검수 → 관리자 검토(운영 CLI와 미리보기) → 발행 → 공개 사이트 반영
- 실측값으로 `thresholds.json`의 `source`를 `judgement`에서 `measured`로 바꾸고 근거를 thresholds.md에 남긴다 (검수 기준 README가 요구하는 항목)
- 후임자 검산을 **처음부터 다시** 수행 (문서 06: 옛 검증 기록은 폐기된 시스템에 대한 것)
- 저장소 충돌 해결 절차 문서 (문서 06의 남은 항목)

**증명하는 방법**
- 발행된 교재가 공개 주소에서 열리고, 영상이 재생되고, 챗봇이 그 본문으로 답한다
- 세 지표가 `pnpm metrics`에서 실측값으로 보인다
- 5단계의 우회 시도 일습을 **운영 환경 빌드에 대해 한 번 더** 돌린다

## 계획이 틀렸을 때 고치는 규칙

1. 계획과 현실이 어긋나면 **이 문서를 고치고** 맨 아래 변경 기록에 날짜·무엇·왜를 남긴다
2. 콘텐츠 계약(1단계 산출물)을 고치게 되면, 그 계약을 읽는 세 소비자(스킬, 사이트, 운영 CLI) 중 무엇이 영향을 받는지 변경 기록에 함께 적는다
3. 단계의 완료 조건은 낮추지 않는다. 조건을 바꿔야 하면 낮추는 것이 아니라 **바꾸는 이유**를 기록하고 사용자 확인을 받는다
4. 새 외부 사업자나 유료 지점이 생기는 변경은 진행 전에 반드시 사용자에게 묻는다
